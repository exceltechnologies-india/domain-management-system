So the widget+token half worked; the server-side verification half was rejecting every token. **Root cause**: the deploy pipeline (`scripts/deploy-cloud-run.sh`) reads sensitive runtime secrets — including `RECAPTCHA_SECRET_KEY` — from **Google Secret Manager** (`--set-secrets="RECAPTCHA_SECRET_KEY=RECAPTCHA_SECRET_KEY:latest"`), NOT from `.env.local`. - [x] **Captcha widget now actually renders on customer-facing forms — the Phase 2 install was tripping on a latent client-side timing bug that took 3 deploy cycles to surface** — after the Phase 2 install (deploy `dms-00181-zvd`) and the key-pair refresh (deploy `dms-00182-8kq`) both shipped, the senior reviewer reported the captcha widget STILL wouldn't render — instead of the "I'm not a robot" checkbox, the page showed a red "Failed to render verification widget" message and the Sign In button stayed disabled. The reviewer tested across Chrome Incognito, Firefox Private Browsing, and Chrome Guest mode — all three showed the identical failure. **Root cause** (took two diagnostic deploys to surface): the project's client-side logger in `lib/logger.ts` is deliberately silenced in production (only `console.*` in development; production routes through a server forwarder), and Cloud Run's stdout/stderr stream for this service was empty during the diagnosis, so the actual underlying JavaScript error was invisible from outside. **Diagnostic patch** (commit `77f3c99`, deploy `dms-00183-4ts`): appended the underlying error message to the user-visible "Failed to render verification widget" text AND added a raw `console.error('[GoogleRecaptcha] render error:', renderError)` that bypassed the production-silenced logger. With that one extra line, the next page-load surfaced the exact error: **"n.render is not a function"** — meaning `grecaptcha.render` was undefined when our code called it. **Underlying bug**: Google's `https://www.google.com/recaptcha/api.js` defines `window.grecaptcha` as a stub object early in its load (the global appears almost immediately), but its public methods (`render`, `reset`, `getResponse`) are wired up asynchronously a few hundred milliseconds later. Our `RecaptchaClient.loadScript()` was polling for the global's existence with `if (g) resolve()` — which resolved on the stub, then `grecaptcha.render(...)` threw because `.render` wasn't there yet. This bug was latent for ~a year — it didn't surface pre-Phase-1 because Google's script init was historically fast enough that `.render` was always attached before we polled. Sometime in the 3-day gap between the Phase 1 rip (2026-06-17) and the Phase 2 install (2026-06-20), Google shifted their script's edge-build timing enough to expose the race. **The real fix** (commit `9765b62`, deploy `dms-00184-bfp` live): the polling loop in `RecaptchaClient.loadScript()` now waits for Google's official `grecaptcha.ready(cb)` callback — the "API is callable now" hook Google publishes for exactly this purpose — with a fallback poll on `typeof grecaptcha.render === 'function'` for cases where Google's edge serves a build of `api.js` where `.ready` itself hasn't landed yet; bounded at 100 tries × 100 ms = 10-second maximum wait, after which the loader rejects with a clear error instead of hanging forever (the original loop was unbounded). The diagnostic carve-out from `dms-00183-4ts` is being kept in place — pairs `console.error` with the production-silenced `logger.error` so the next regression is visible in one DevTools refresh. **Verified by the senior reviewer end-to-end on `dms-00184-bfp`** — the "I'm not a robot" checkbox now renders cleanly, ticking it enables the Sign In button, and the post-submit reCAPTCHA token verifies successfully on the server. **Prevention measures**: (1) the loadScript polling-gate pattern is documented in auto-memory as `project_recaptcha_ready_gate` so future Claude Code sessions don't repeat the diagnostic detour; (2) the `console.error` carve-out for widget-init errors is documented as `feedback_diagnostic_console_error` and should be applied to any future third-party-widget loader (Razorpay, Stripe Elements, etc.) so production logger suppression never again blocks a real customer-facing failure mode (deploys `dms-00183-4ts` diagnostic + `dms-00184-bfp` real fix both live; previous attempts `dms-00181-zvd` + `dms-00182-8kq` shipped earlier today and were the right code with the wrong ready-gate)
